# Technical Debt Register

Shortcuts and gaps the team has knowingly accepted, so they are tracked and not forgotten. Added in M3 (13 October 2026) with the authentication branch; each later slice adds its own rows. Status is Open unless stated.

| ID | Debt item | Where | Why accepted now | Consequence if left | Repay when / how | Linked |
|---|---|---|---|---|---|---|
| TD-01 | No login rate limiting or account lockout | `app/api/auth/login/route.ts` | M3 scope and time; the password hash is deliberately slow (scrypt) | Someone can guess passwords without being slowed down | Before real users: add a per-email and per-address attempt limit | R-13 |
| TD-02 | No revocation of a single session | `lib/auth/session.ts` (stateless signed cookie, ADR-06) | A session table would add a migration and a database read on every request | A stolen cookie works for up to 8 hours; only rotating `SESSION_SECRET` signs everyone out | If real data is held: move to database-backed sessions or add a token version per user | R-13, ADR-06 |
| TD-03 | Password reset and email verification not built | Sign-up and sign-in flow | Deferred scope (CR-009) | A forgotten password needs a manual database change; accounts can be made with an email the person does not own | When email sending exists (notifications are also deferred) | CR-009, FR-001 |
| TD-04 | `admin` role exists in the schema but is not used | `lib/db/schema.ts`, `lib/auth/guard.ts` | No admin screen in M3 | Unused role may suggest a feature that does not exist | Build the admin screen or remove the role | CR-009 |
| TD-05 | API tests mock the database | `tests/api/auth/*.test.ts` | Tests must run in CI without a database or secrets | SQL, constraints and the unique-email index are only checked by hand on Neon | Add integration tests against a test database (for example a Neon branch or a local Postgres) | R-13, M3 integration evidence |
| TD-06 | No automated test for `getCurrentUser`, `readSession`, sign-out or the sign-in and sign-up screens | `lib/auth/guard.ts`, `lib/auth/session.ts`, `components/auth/` | They need a cookie store, a database or a browser | A break there is only caught by manual checks until end-to-end tests exist | Cover with end-to-end tests later in M3 | NFR-004 |
| TD-07 | Pages other than sign-in and sign-up still read sample data | `lib/mock/data.ts` and the pages that import it | The request, staff and manager routes are built slice by slice | The app looks complete but most screens are not backed by the database | Replace page by page as each slice is built, then delete the mock file | RTM UI Reference |
| TD-08 | `SESSION_SECRET` is only checked for length | `lib/auth/session.ts` | Keeps the check simple | The placeholder from `.env.example` would be accepted if copied unchanged | Reject the placeholder value in production or before the staging deploy | R-13 |
| TD-09 | Sign-in and sign-up redirect with a full page reload | `components/auth/LoginForm.tsx`, `RegisterForm.tsx`, `components/layout/Header.tsx` | The root layout must re-read the new session cookie, and a client-side redirect showed a stale signed-out header | Slightly slower page change after sign-in; a lint rule is switched off on the redirect lines with an explanatory comment | Replace with a router refresh once the layout reads the session in a way that updates | n/a |
